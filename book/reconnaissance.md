# Reconnaissance and Blueprint Decisions

Audit baseline: `/Users/daman/github.com/aroradaman/substrate`, commit `0ddbf78d54bb6da2ccb01125b7e085aa14d555a6`, October 31, 2026. The original request was reconnaissance followed by an approval gate. The user subsequently authorized writing the complete book and explicitly added RustFS coverage. This document preserves the blueprint reasoning behind that manuscript.

## Phase 1: architecture inventory

The inventory covered the whole local clone, including hidden contributor/CI directories, dependency source, runtime provenance, demos, benchmarks, deployment overlays, generated code, and documentation tooling. [Appendix B](appendix-b-source-inventory.md) records the counts, component ownership, protocol map, and implementation-status matrix.

The original directory assumptions did not match the checkout. There is no `pkg/apis`, `config`, `deploy`, or `cmd/ateom`. Infrastructure types are under `api/infra/k8s/ate/v1`; public workload protocols under `api/ateapi/v1`; deployment files under `manifests`; runtime implementations under `cmd/ateworker-gvisor` and `cmd/ateworker-microvm`. The architecture document is `docs/concepts/architecture.md`. No `docs/roadmap.md` exists locally, and a check of the corresponding upstream main URL also returned not found during reconnaissance.

The largest conceptual correction is the two persistence planes. Actor and ActorTemplate are API records in PostgreSQL. WorkerPool, SandboxConfig, and CSIDriverConfig are Kubernetes CRDs. A second correction is concurrent multiplexing: one worker can host several active actors, in addition to reusing its capacity across suspend/resume cycles. A third is controller placement: golden-snapshot and assignment-recovery work runs inside ateapi, while not all controller code uses controller-runtime.

## Phase 2: Linux audit

[Appendix A](appendix-a-kernel-audit.md) contains the requested four-column table with exact local source paths. It separates direct calls, checked wrappers, runtime-mediated mechanisms, and test/benchmark-only operations. Runtime commands, SQL locks, TLS, and gRPC are identified at their own layers rather than mislabeled as syscalls.

The audit found that the default CH v53.0 asset selection currently chooses eager Copy restore. OnDemand/userfaultfd remains an implemented alternative governed by a version check. Sparse delta merging already exists, but it produces complete snapshots instead of a remote delta chain. Both outer worker classes explicitly use Unconfined seccomp and AppArmor despite some nearby older comments. MicroVM rootfs upper layers are host-backed. These findings materially changed the chapter plan.

## Phase 3: outline critique

The initial outline identified the main concerns, but its component names and balance were outdated. Its first two chapters can be combined for this audience: a Kubernetes core contributor does not need a long general argument that Pods are inadequate. A precise explanation of actor lifecycle, warm capacity, active sharing, and state movement provides a better opening.

The control plane needs more than API plumbing and a placement heuristic. Renewable SQL leases, row-locked capacity admission, unique assignments, worker epochs, workflow reentry, and the transactional worker-event stream establish the actual consistency model. The book gives that model a full chapter and moves storage-specific state machines into the persistence chapter to keep it manageable.

The former sandboxing chapter is split into gVisor and microVM chapters. Their host process models, memory accounting, filesystem ownership, networking, checkpoint formats, entropy/time repair, and compatibility assumptions are sufficiently different to require separate treatment. Snapshot storage becomes its own chapter rather than a short continuation of runtime checkpointing.

Networking retains a full chapter, expanded to include request parking, namespace lifetime, DNS transport, CONNECT behavior, the embedded atunnel library, Rust Envoy modules, and AgentGateway. Identity and policy remain separate because a transport route and authorization decision have different evidence and failure modes. Operations includes benchmark interpretation and CI limitations. The final chapter owns extension and upgrade contracts; each subsystem's N.6 carries its specific future work.
